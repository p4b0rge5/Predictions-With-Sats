## System Design

### Data Flow

1. **User enters app** → Sees current BTC price, timer countdown, recent history
2. **User places bet** → Enters USD amount → Clicks UP/DOWN
3. **Backend generates invoice** → Via Alby API → Returns QR code
4. **User pays invoice** → Lightning payment → Alby confirms
5. **Webhook notifies** → Bet marked as "paid" in DB
6. **Window closes** (5 min) → Oracle fetches final price
7. **Outcome determined** → Winners calculated → Payouts queued
8. **Payouts sent** → Via Alby to winner's wallet

### Key Design Decisions

| Aspect | Decision | Rationale |
|--------|----------|-----------|
| **Database** | SQLite | Simple, single file, zero config |
| **Payments** | Alby LSP | No node required, instant setup |
| **Frontend** | Vanilla JS | Fastest load, no build step |
| **Price Oracle** | Multi-source | Resilience, manipulation resistance |
| **Settlement** | 30s buffer | Prevents last-second arbitrage |

### Database Schema

```sql
market_windows    -- 5-minute betting windows
bets             -- User bets with payment tracking
price_snapshots  -- Price data from multiple sources
webhook_events   -- Payment webhook log
```

### API Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/health` | Server status |
| GET | `/api/market/current` | Current window + price |
| POST | `/api/bet` | Create bet + invoice |
| GET | `/api/bet/:hash` | Check bet status |
| POST | `/api/webhook/alby` | Payment notifications |
| GET | `/api/market/history` | Recent results |
| GET | `/api/stats` | Platform stats |

### Security Considerations

- No user accounts (LN wallet = identity)
- No fund custody (LSP holds temporarily)
- Webhook signature verification
- Rate limiting (to be implemented)
- Input validation on all endpoints
